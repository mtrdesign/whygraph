# WhyGraph 2.7.0

A production platform gets an admin panel at `/admin`, with its own sign-in and session. From it an
administrator manages users, organizations and projects, suspends an organization, deletes and
restores without erasing anything, and reads an organization only through a short read-only grant.
A Dashboard shows spend, scans and disk use, and a Configuration page decides who can sign up and
who can create organizations. A local portal changes only underneath: its database is upgraded, and
nothing you use looks different.

!!! warning "Production: hand over the bootstrap account's organizations"
    Password accounts, the bootstrap administrator included, can no longer sign in to an organization;
    they sign in to platform administration at `/admin/login`. If the password account owns an
    organization, make a GitHub user its owner after the upgrade, then remove the password account from
    it. Its connection tokens are revoked. The steps are in
    [Platform administration and password accounts](../portal/upgrading.md#admin-mode). A local portal is
    not affected.

!!! note "Upgrading and rolling back"
    From 2.6.0, run `whygraph update` (locally) or move the production image tag to `2.7.0`. The portal's
    own database is upgraded when it starts; project databases are unchanged. In production, hand over
    the password account's organizations afterwards (above). To go back, see
    [Rolling back after this release](#rolling-back).

## What's new

- **Platform administration.** Production instances get an admin panel at `/admin` on the base host,
  with its own sign-in (GitHub, or the bootstrap password) and its own 8-hour session that an
  organization host never sees. Its modules are the Dashboard, Projects, Organizations, Users, Audit
  and Configuration. See [Platform administration](../deploy/administration.md).
- **The password account is for administration only.** `POST /api/auth/login` and the sign-in page's
  "Administrator sign-in" are gone, and so is changing a password from the everyday Account page: it is
  on the admin Account page now.
- **Manage organizations and users from the panel.** Organizations and Users have detail pages: create
  an organization, rename it, change its members and roles, and see its projects, spend and audit.
  An administrator can **suspend** an organization (everyone gets read-only access and a banner with the
  reason), and **delete** users, organizations and projects without erasing anything: each can be
  restored, or deleted permanently. A deleted user reads as `[Deleted User]`, and **Erase
  permanently** removes their personal data. See
  [Platform administration](../deploy/administration.md).
- **Reading an organization is a grant.** An administrator no longer reads every organization all the
  time: **Open as reader** gives a 60-minute read-only grant, shown to the organization's people in a
  banner and revoked from the Account page.
- **Removing a project, or an organization, only hides it in production.** An owner or admin who
  removes one no longer deletes it: a platform administrator can restore it or delete it permanently.
  The import picker shows a removed repository as removed.
- **The cross-organization audit log** has an Organization filter and column and a CSV download.
- **A real Dashboard and a Projects module.** The admin Dashboard lists what needs attention, shows
  seven figures and three charts (LLM spend, scans, the top organizations) for a date range you pick,
  and every project has a page with its scans, logs, Rescan and storage. Organizations and projects
  show how much disk they use, measured by the portal every six hours. See
  [Platform administration](../deploy/administration.md#dashboard).
- **Decide who can sign up.** The admin panel's **Configuration** page sets the platform's policy
  without a restart: who can sign up (anyone with a GitHub account, the default; invited people and a
  **sign-up allowlist**; or nobody new), whether only administrators can create organizations, a limit
  on the organizations one person may own and on the projects per organization, and an **announcement
  banner** shown on every page, signed in or not. It also shows the instance's address check, version
  and update status, and disk use. A new platform still starts open: close it if you do not want
  strangers on it. See [Who can sign up](../deploy/production.md#sign-up) and
  [Platform administration](../deploy/administration.md#configuration).
- **New security events** for everything the panel does: `admin_signin`, `admin_signin_refused`,
  `admin_signout`, `reader_grant_created` / `reader_grant_revoked`, `org_suspended` /
  `org_unsuspended`, the delete, restore, purge and erase events of users, organizations and
  projects, `project_scan_requested` / `project_scan_cancelled`, `sessions_revoked`,
  `instance_settings_changed` and `signup_allowlist_changed`. See
  [the security event log](../deploy/production.md#the-security-event-log).

## Changes to know about

- **Removed routes.** `POST /api/auth/login`, `POST /api/account/password`, `GET /api/admin/settings`
  and `GET /api/admin/update` are gone. The admin panel's routes under `/api/admin` take an admin
  session only; an everyday session gets `401 admin_login_required`.
- **The update notice moved.** In production it is an attention item on the admin Dashboard and a line
  in Configuration's Instance card, in place of the old Updates card. The local banner is unchanged.
- **A removed project keeps its data in production** until a platform administrator purges it, so the
  disk is not freed when an owner removes a project. The Dashboard lists deleted items that still hold
  data.

## Rolling back { #rolling-back }

This release adds tables and columns to the **portal's own database** (four migrations, below);
project databases are unchanged. Migrations only go forward, so a 2.6.0 image cannot start on the
upgraded database. To go back, restore the dump taken before the upgrade (`whygraph update` makes one; in
production, the backup from step 2 of [Upgrading](../deploy/production.md#upgrading)), following
[Restore](../portal/backup.md#restore), then re-run the installer from the `v2.6.0` tag (or move the
image tag back) and start the portal. Anything done in the admin panel since the upgrade is lost with
the newer database.
