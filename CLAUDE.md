# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

WhyGraph 2.0 (milestone M1, the **portal MVP**) is the Python implementation. The per-repo 1.x workflow (`whygraph init`, `whygraph serve`, the stdio `whygraph-mcp` server) is gone; **the portal replaces all three.** Live components: the **portal** (`whygraph up` on the host, `whygraph portal` in the image) - one long-running FastAPI process that holds many projects, runs every scan as a child process, serves the React playground (Explorer + **Chat**, per project at `/p/<slug>/...`) and a per-project **HTTP MCP endpoint at `/mcp/<slug>`** (evidence / area-history / rationale tools with the SQLite-backed content-addressable cache, repo / commit / PR / issue resources, orchestration prompts); its own **Postgres** DB (projects, config layers, Fernet-encrypted keys, scan runs; since 2.1 - M2a, `plans/m2a-postgres-plan.md`); the CLI (`scan` - mostly the portal's child process, also headless for CI - `portal`, `install`, `version`, plus removal stubs); the Docker host verbs `up` / `down` / `status` / `logs` / `folders` / `backup`; the Chat assistant (an in-house streaming tool-calling harness over OpenRouter / OpenAI / Anthropic / DeepSeek, sessions in each project's WhyGraph DB; see `plans/chat-assistant-plan.md`); and the `/whygraph-plan` slash command + fan-out/fan-in planner subagents. The M1 plan is `plans/m1-portal-mvp-plan.md` (gitignored). The earlier *static HTML* render viewer was removed during the III iteration migration; the original TypeScript POC was retired; pre-`85fe8b3` commit history covers the v0 design for archaeology.

Core architectural decisions that still apply — read these before adding architecture:

- **Graph backend abstraction.** A `GraphBackend` Python protocol (`get_node`, `get_callers`, `get_callees`, `find_symbols`, `walk_neighbors`) with `SqliteCodegraphBackend` as the first impl (reads CodeGraph's SQLite directly — no subprocess, no MCP roundtrip). Other backends (`JsonGraphifyBackend`, `MCPBackend`) drop in later without re-architecting.
- **Plugin shape, in order.** (1) MCP tools `whygraph_rationale_brief` and `whygraph_evidence_for`. (2) A `/whygraph-plan <task>` slash command that spawns a Plan subagent via the `Agent` tool with rationale cards **inlined at spawn time**. (3) Workers after the planner.
- **WhyGraph's MCP surface stays narrow** — rationale + evidence cards only. Users who want raw graph queries install the graph backend's own MCP server alongside.
- **Cache key must be content-addressable** (hash of `qualified_name + file_path`, not the backend's `node_id`) so cards survive a backend swap.
- **One process, many projects, via a context seam.** `core/context.py` binds a `ProjectContext` (slug, root, `Config`) with `use_project()`; `get_config()`, `_resolve_root()` and `db/engine.py` consult it first, and **strict mode** (on for the portal's lifetime) makes an unbound lookup raise instead of guessing from `cwd`. Every request / MCP call / chat turn runs under the project it serves. Fan-out to threads must copy the context explicitly.
- **Two kinds of database.** The portal's own DB (`portal/`, Postgres at `$WHYGRAPH_DATABASE_URL`; locally the shim's `<portal>-postgres` container with its files in `$WHYGRAPH_DATA/postgres`) holds projects, config layers, encrypted secrets and scan runs; each project's `whygraph.db` and `codegraph.db` stay **in its repo** at forced default paths, so removing a project never deletes history.
- **A repo is untrusted input.** Nothing a repo commits may widen what the portal reads or writes: import is an allowlist, DB paths are forced, and `core/safe_paths.py` refuses symlinks that leave the root. Do not add a read or write of a repo path that skips `check_inside`.

## Common commands

The project is uv-managed (Python ≥ 3.11, pinned via `.python-version`).

```bash
uv sync                       # bootstrap .venv and install deps
uv run pytest                 # all tests (the portal tests need Docker or WHYGRAPH_TEST_DATABASE_URL)
uv run pytest tests/test_smoke.py::test_imports   # single test
uv run whygraph version       # CLI sanity check
make dev-local                # develop natively: portal (:8777, auto-restart) + Vite HMR (:5173) on `make dev-db`'s Postgres; open :5173
make dev-docker               # the same inside the image via the real shim (checkout mounted over the package)
make prod                     # the image built like the release, through the shim, no mount
make check                    # lint + pytest + frontend + e2e + scripts/smoke.sh on a fresh image
make docs                     # serve the documentation site locally with live reload
make docs-build               # build it strictly (what CI runs)
```

`whygraph-mcp` no longer launches a server: it is a stub that prints the removal message and exits 2 (the MCP server runs inside the portal at `/mcp/<slug>`; `make inspect SLUG=<slug>` points the MCP Inspector at it). A root `Makefile` wraps these plus dev-only tooling — `make` lists targets; `make db` / `make db-down` run a DBGate viewer for a scratch repo's two databases (via `docker-compose.example.yml`), `make inspect` launches the MCP Inspector. Every dev mode is isolated from the user's own portal (own container name, data dir and HOME under `$TMPDIR/whygraph-dev`) and shares only the offline scratch repos in `$TMPDIR/whygraph-dev/repos`, never this checkout; the Docker modes use two dev-only shim knobs, `WHYGRAPH_DEV_SRC` and `WHYGRAPH_PORTAL_NAME` (see `docs/guide/developing.md`).

## Documentation site

`docs/` is a **Material for MkDocs** site published to <https://mtrdesign.github.io/whygraph/> by `.github/workflows/docs.yml` on every push to `main` that touches `docs/**`, `mkdocs.yml`, or `pyproject.toml`. It is the **source of truth for user-facing docs** — the README is deliberately trimmed to a pitch plus a pointer, because a duplicated README is what rotted last time.

Two things follow from that:

- **A user-visible change is not done until `docs/` says so.** New CLI flags, config keys, MCP tools, and UI surfaces all have a reference page that must move with them. Nav lives in `mkdocs.yml`.
- **Run `make docs-build` before pushing a docs change.** It builds with `--strict`, so a broken internal link fails the build rather than shipping a 404. Social cards only generate under `CI=true`, so a local build needs no Cairo/Pango.

Prose style: **plain hyphens, not em dashes** (enforced by convention, not a linter — see `69e23c7`). Admonitions, grid cards, and tabbed blocks are all available; see `mkdocs.yml` for the enabled extensions.

## Before pushing

CI (`ci-code-checks`) gates every PR on three parallel jobs: **lint** (`uv run ruff check src/ tests/ scripts/` *and* `uv run ruff format --check src/ tests/ scripts/` — both, not just the first), **tests** (`uv run pytest`), and **frontend** (in `src/playground/`, Node 22: `npm ci`, `npm run typecheck`, `npm test` (Vitest), `npm run build`). `scripts/` is linted but **not** collected by pytest (`testpaths` is `tests/`) — it holds live-provider tooling that must never gate CI. The **tests** job runs against a `postgres` service container (`WHYGRAPH_TEST_DATABASE_URL`, image gated against `POSTGRES_IMAGE`); locally, `uv run pytest` starts a throwaway Postgres container itself, so it needs Docker or `WHYGRAPH_TEST_DATABASE_URL` (an admin URL) - without either the portal tests fail, never skip. Run the three Python commands locally before pushing or opening a PR - and, when you touched `src/playground/`, the frontend ones too (Node >= 22.12, so `nvm use 22` first):

```bash
uv run ruff check src/ tests/ scripts/
uv run ruff format --check src/ tests/ scripts/   # `ruff check` passing does NOT imply this passes
uv run pytest
npm --prefix src/playground run typecheck && npm --prefix src/playground test && npm --prefix src/playground run build   # frontend changes only
```

If `ruff format --check` fails, run `uv run ruff format src/ tests/ scripts/` to fix it in place, then re-run the check before pushing.

## Architecture

Top-level packages under `src/whygraph/`:

- `cli/` — Click group + one module per subcommand under `cli/commands/` (`scan`, `portal`, `install`, `version`; `init` and `serve` are hidden stubs). `cli/stubs.py` holds the removal messages and `removed_command()` (print to stderr, exit 2) plus the `whygraph_mcp` console-script stub; `analyze` was removed outright and the interactive `init` prompts (`cli/interactive.py`) are gone. `cli/__init__.py` assembles the group, configures logging once per invocation, and exports `main`. Shared console formatting lives in `cli/console.py`. `scan` refuses in a repo with a valid untracked `.whygraph/portal.json` marker unless the portal's hidden `--managed-by-portal` is passed, and `--progress json` makes it the portal's machine-readable child process (`scan/json_progress.py`).
- `portal/` — the multi-project host, and the centre of 2.0. `app.py` is the FastAPI factory `create_portal_app` (mounts the management routes at `/api`, each project's Explorer and Chat routers under `/api/projects/<slug>`, the MCP endpoint at `/mcp/<slug>` via `mcp_mount.py`, then the SPA). `db.py` / `models.py` / `migrations/` are the portal's **own** Postgres DB on a private `MetaData` (never mixed with a project DB; `db.py` holds the URL resolution, the start-up wait and the advisory `InstanceLock`); `secrets.py` the Fernet store (write-only through the API); `config_layers.py` + `policy.py` the global/project config layers and the allowlists every write goes through (rules 1a/1b/4/6); `context.py` builds a `ProjectContext` from those rows (`ContextCache` - **every endpoint that writes config or secrets must invalidate it**); `runner.py` runs scans as `whygraph scan --progress json` children (single-flight per project, union-coalescing, at most two at once; `estimate.py` is the first-scan cost guard); `security.py` is the Host / Origin / `X-WhyGraph-Client` guard; `repos.py` the shared-folder checks and discovery; `port_change.py` follows a port change into repo markers and agent files. **The portal is exactly one process**: state lives in memory (runner, caches, the MCP session manager), it holds `<data>/portal.lock` plus a Postgres advisory lock on its database, and it must never run with `--workers`.
- `mcp/` — the WhyGraph MCP surface, now served over HTTP by the portal (`portal/mcp_mount.py`, one stateless Streamable HTTP endpoint per project) - the 1.x stdio entry point is gone. `server.py` builds the single `FastMCP("whygraph")` instance and `offload`s every sync tool body to a worker thread; feature modules (`evidence.py`, `rationale.py`, `rationale_cache.py`, `targets.py`, `errors.py`) each register their tools via a `register(mcp)` function, so new MCP features land as new modules without growing a monolith.
- `core/` — cross-cutting helpers: `config` (config v2: `Config.from_dict`, `normalize_v2`, `merge_v2`, per-task `model_for`), `context.py` (the project-context seam, see above), `safe_paths.py` (`check_inside`: no symlink component under a root, resolved path stays inside - the one guard for every repo path the portal touches), `logger` (logging setup), `shell` / `shell_command` (subprocess helpers), `utils`, `gitignore`.
- `project_setup.py` — `initialize_project()`, what the portal's Initialize step does to a repo: `.gitignore` entries, hooks, per-agent HTTP MCP entries + assets, and (last) the `.whygraph/portal.json` / `portal.env` markers. A library, Click-free, prints nothing; DB bootstrap and config stay in the caller.
- `db/` — SQLite plumbing. `engine.py` + `bootstrap.py` set up the DB, `base.py` is the declarative base, `models/` holds the SQLModel classes, `migrations/` holds Alembic versions.
- `serve/` — the Explorer and Chat **routers**, mounted by the portal per project (there is no `whygraph serve` any more, and no `create_app` here). `routes.py` and `chat.py` are the data routes; `app.py` only serves the built SPA from `static/`; `graphdata.py` shapes CodeGraph reads for the UI; `coverage.py` computes rationale coverage. **Every handler is a sync `def`** — FastAPI runs them in the threadpool, one `get_session()` and one `CodeGraph` handle per request, under the project the URL names. The React source lives in `src/playground/` (React 19, Tailwind 4, shadcn, TanStack Router) and builds into `serve/static/`.
- `chat/` — the Chat view's agentic harness (a third adapter over the same core as `mcp/` and `serve/`). `tools.py` holds the 17 tool specs + `ToolRegistry` (instantiated **once per user turn** — it carries the rationale-generation budget); `files.py` is the clamped read-only file access; `stats_sql.py` is the statistics surface — read-only, **aggregate-only** SQL behind a SQLite authorizer, with a table allowlist that denies `chat_*` and `rationale_cache` (see its module docstring for the four layers); `harness.py` is `run_turn` (the tool loop) and `build_window` (token-budgeted context trimming); `prompts/system.md` is the packaged system prompt. The harness is **persistence-free** — `serve/chat.py` owns every row.
- `services/` — external integrations: `git/`, `github/`, `codegraph/` (reads CodeGraph's SQLite by `node_id`), `llm/` (Anthropic / OpenAI / OpenRouter / DeepSeek / Ollama / claude-cli). Two **parallel ports** live here: `client.py`'s `LlmClient` (sync `complete()`, used by analyze/rationale) and `chat.py`'s `ChatClient` (streaming + tool-calling, used by `chat/`). They are deliberately separate — see `chat.py`'s docstring.
- `scan/` — crawler orchestration. `crawler.py` drives `git_crawler.py`, `github_crawler.py`, and `analyze_crawler.py` per-source phases.
- `analyze/` — LLM-backed analysis. `description.py` / `llm_descriptor.py` produce per-commit diff descriptions; `rationale.py` / `rationale_generator.py` produce the 5-section rationale cards; `backfill.py` runs the lazy on-read backfill. Prompt templates live under `analyze/prompts/`.
- `agents.py` — registry of the four supported LLM agents (Claude Code, Cursor, VS Code / Copilot, Codex — Claude Desktop was dropped) and the per-agent **HTTP** MCP config wiring: `HttpMcp.url_for` (the per-agent port form - Claude Code `${WHYGRAPH_PORT:-<port>}`, VS Code an `inputs` prompt, Cursor and Codex a **literal** port), `apply_http_entry` (refuses unparseable JSONC / commented TOML, backs up, needs confirmation for git-tracked files), `detect_entries`, `remove_entry`. All four are project-scoped and **all four ship an asset tree**. The portal's Initialize step reads from here.
- `assets.py` + `assets/claude-code/` — bundled Claude Code assets (agents, commands, skills) copied into a project's `.claude/` by the portal's Initialize step. Loaded at runtime via `importlib.resources.files("whygraph") / "assets" / "claude-code"`; same packaging precedent as `analyze/prompts/`.
- `hooks.py` — the auto-rescan git hooks (`post-commit` / `post-merge` / `post-rewrite` / `post-checkout`): the helper script, the sentinel-guarded dispatcher, and `sync_hooks()`. A top-level module for the same reason as `agents.py` / `assets.py` — an installed-by-the-portal concern — and deliberately Click-free (it raises `HooksError`, not `ClickException`).
- `__main__.py` — enables `python -m whygraph`.

Console scripts in `pyproject.toml`: `whygraph` → `cli:main`, `whygraph-mcp` → `cli.stubs:whygraph_mcp`. Both must keep working, but the second is now a **removal stub** (message on stderr, nothing on stdout, exit 2), not a server: every 1.x `.mcp.json` that still runs `whygraph-mcp` must get that message rather than "command not found", and the `uv tool install` path depends on the script existing. The host installer writes a matching `whygraph-mcp` stub that never calls docker. There is no `mcp.server:main` any more.

## Install path

WhyGraph installs **once per machine**; projects are added in the portal, not wired by a command:

1. `curl -fsSL …/install.sh | sh` (see below) puts the `whygraph` shim (and the `whygraph-mcp` removal stub) on `PATH`. `uv tool install whygraph` / `pipx install whygraph` provide **headless `whygraph scan` only** - the portal needs the Docker install.
2. `whygraph up` starts the portal; the user opens it in a browser, shares a folder that holds their repos (`whygraph up --add-folder DIR`), and **adds each repo from the Projects page**. The portal's Initialize step (`project_setup.initialize_project`) does what `whygraph init --agent X` did, with a per-file preview: `.gitignore` entries, the four git hooks, and for each selected agent an **HTTP MCP entry** plus its bundled asset tree - `claude` → `.mcp.json` + `.claude/`, `cursor` → `.cursor/mcp.json` + `.cursor/`, `vscode` (alias `copilot`) → `.vscode/mcp.json` + `.github/`, `codex` → `.codex/config.toml` + repo root + `.codex/agents/`. Every agent's asset install also drops a **CodeGraph usage-guidance block** into that agent's always-on instructions (`.claude/CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md` via append-merge; an `alwaysApply: true` rule for Cursor) so the agent prefers the `codegraph_*` tools over grep without the user running CodeGraph's own installer.

Agent entries are **commit-safe on the default port** (Claude Code `${WHYGRAPH_PORT:-8765}`, VS Code an `inputs` prompt, Cursor and Codex a literal `8765` because Cursor documents no default for `${env:...}`). A git-tracked agent file is written only after a diff preview and confirmation, an unparseable one is refused with a snippet, and a port change never rewrites a tracked file.

There is no Claude Code marketplace install. The bundled assets are version-controlled in this repo under `src/whygraph/assets/claude-code/` - that is the source of truth, the wheel ships them, and re-initializing from the portal ("Update agent files") brings a project's `.claude/` up to date.

## Docker delivery (the default install)

WhyGraph ships as a self-contained image so a developer needs **only Docker** on the host — no Python / Node / gh / codegraph install. The image is the only thing that gets installed; the **front door is a tag-pinned `curl … | sh`** (`scripts/install.sh` fetched from `raw.githubusercontent.com`). The whole UX is three steps - **install → `whygraph up` → browser**:

```bash
curl -fsSL https://raw.githubusercontent.com/mtrdesign/whygraph/v2.0.0/scripts/install.sh | sh
whygraph up       # start the portal (one long-lived container, 127.0.0.1 only)
# open http://127.0.0.1:8765 and add a repo from the Projects page
```

**Two components, one generator.** `scripts/install.sh` is a **host-side bootstrapper** — it probes `docker` + the daemon, pulls the pinned image, then delegates to `docker run --rm <image> whygraph install` and executes that output only after checking it is **non-empty**. It carries **no shim bodies**; the in-image **`whygraph install` command** (`cli/commands/install.py`) is the single generator, writing the `whygraph` **shim** and a `whygraph-mcp` **stub** onto PATH. The shim wraps `docker run --rm -v "$PWD:/workspace" -w /workspace <image> whygraph "$@"` for everything except the portal verbs (below); the stub only prints the removal message and never calls docker. That split is load-bearing: shim bodies stay in tested Python (`tests/test_install_cmd.py`) and the shell script stays thin enough that a frozen per-tag copy can't be wrong about WhyGraph. `tests/test_install_script.py` asserts the absence of shim bodies, the `main "$@"` truncation-safe shape, and that **every** failure path exits non-zero — the old `docker run … install | sh` front door exited **0** when it installed nothing, because docker's error went to stderr and `sh` read an empty stdin.

The `docker run … whygraph install | sh` form remains supported (no-curl / air-gapped / CI) and, without the pipe, is the way to inspect what would be written. The bare-`install` **launcher** (`/usr/local/bin/install`) was **removed** — call the command explicitly. There is deliberately **no `ENTRYPOINT`** so `docker run <image> codegraph …` and `<image> whygraph …` still resolve. The shim bakes `ghcr.io/mtrdesign/whygraph:<version>` from the image's `WHYGRAPH_VERSION` (baked at build), so an install **pins the concrete release** even via `:latest`; the shim still honours a `WHYGRAPH_IMAGE` override at run time. The container is **ephemeral per command** — no compose, no `docker exec` — with exactly one exception: the **portal container and its Postgres container**. The shim's host verbs `up [--port N] [--add-folder DIR]` / `down` / `status` / `logs` / `folders [--remove DIR]` / `backup` manage the **named, long-lived** `whygraph-portal` container (`--restart unless-stopped`, `-p 127.0.0.1:<port>`, its own `whygraph-portal` Docker network, `--add-host=host.docker.internal:host-gateway`, `--init`). Shared folders are bind-mounted at the **same path** as on the host (`--mount type=bind`, which errors on a missing source rather than creating it root-owned), the data dir (`~/.local/share/whygraph`, mode 0700) at `/data`; the folders / port / image are recorded as container labels and any difference recreates it (`stop -t 30` + `rm`, so a running scan child is recorded as interrupted). `~/.config/whygraph/{folders,port}` hold the host-side state. Beside it, `<portal>-postgres` (`POSTGRES_IMAGE` in `install.py`, an exact Debian-trixie tag whose variant never changes; `WHYGRAPH_POSTGRES_IMAGE` overrides) runs on the same network with **no published port**, `$DATA/postgres` bind-mounted at `/var/lib/postgresql` with a per-major `PGDATA`, and a generated 0600 `$DATA/postgres.password` passed to both containers as a file; `up` waits for its `pg_isready -h 127.0.0.1` health check, dumps a running database (`whygraph backup`, `$DATA/backups`, newest 10) before recreating it, refuses another major's data, and `down` / `status` cover both containers. **Nothing from the host environment is passed in** - keys and tokens live encrypted in the portal DB, and the first `up` that sees one set prints a one-time hint naming (never showing) them. `serve` in the shim is a stub that prints the removal message (its `--stop` still removes a leftover 1.x `whygraph-serve` container). The image is built from `docker/whygraph/Dockerfile` (base `python:3.12-slim` + git + gh + Node 22 + pinned CodeGraph CLI + pinned Claude Code CLI + WhyGraph) and published by `.github/workflows/cd-deploy-whygraph.yml` (which passes `WHYGRAPH_VERSION` + pinned `CODEGRAPH_VERSION` / `CLAUDE_CODE_VERSION` as build-args; `make image` reads the same pins). The `claude-cli` provider runs in the image on a **Claude subscription token** (`claude setup-token`, stored as the `claude_oauth_token` portal secret) exported only to `claude` as `CLAUDE_CODE_OAUTH_TOKEN`, with a private throw-away `CLAUDE_CONFIG_DIR` per call - never a mounted `~/.claude` (on macOS the login is in the Keychain).

**The version is written once, in the URL** — the tag names it and `DEFAULT_VERSION` in `scripts/install.sh` matches, so `-s <ver>` / `WHYGRAPH_VERSION` are overrides, not requirements. That makes a **per-release ritual**: bump `DEFAULT_VERSION`, `pyproject.toml`, the README URL, *and* every pinned literal under `docs/` to the release being cut. Two gates enforce it, because discipline alone demonstrably fails here (`pyproject.toml`'s `version` went unbumped through v1.0.0, and `docs/` went ungated until the v1.1.1 docs refresh) — `tests/test_install_script.py` checks script-vs-README-vs-pyproject-vs-`docs/` agreement on every PR, and a step in `cd-deploy-whygraph.yml` checks all four against the release tag **before** the image is pushed. The docs gate covers the three pinned forms (the `curl` URL, `ghcr.io/mtrdesign/whygraph:<ver>`, `whygraph.git@v<ver>`) plus every bare semver on the two install-only pages. A forgotten bump is a red release, not a wrong pin. A per-tag script is frozen, so `…/main/scripts/install.sh` is the documented valve for an installer bug.

Invariants that keep the shim correct — preserve them:

- **Each ephemeral command is a fresh process against `cwd`; the portal is the one process that serves many projects, and only through the context seam.** For a one-shot `whygraph scan`, `get_config()` is globally memoized and config / DB-path discovery walks up from `cwd` to the `.git` root (`core/__init__.py`, `db/engine.py`); the shim mounts the repo at `/workspace` and runs there. Inside the portal nothing may rely on `cwd`: strict mode (`core/context.py`) makes an unbound lookup raise, and the portal's scans are child processes with their own `cwd`. Don't reintroduce an in-process loop over several repos outside `use_project()`.
- **Host-user file ownership.** The shim runs `--user "$(id -u):$(id -g)" -e HOME=/tmp` so `.whygraph/` and `.codegraph/` come back owned by the host user and git sees matching ownership (no "dubious ownership"). Keep these when editing the shim.
- **GitHub token is per-project.** In the portal it is a per-project (or global) **secret** in the portal DB, injected into that scan child's env as `GH_TOKEN` (and never into `.git/config`, argv, logs or run files). For *headless* `whygraph scan`, `[scan].token` in the repo's `whygraph.toml` (gitignored) is exported as `GH_TOKEN` (`cli/commands/scan.py:_apply_github_token`), falling back to ambient `GH_TOKEN` / `GITHUB_TOKEN` (the ephemeral shim path still passes those through; the portal container never gets them). Do **not** bake a token into the image or assume a container-wide token.
- **The child-env allowlist is shared.** A scan child, and every `git` / `gh` the portal spawns, gets only `services/git/credentials.py:pass_through_env` plus the one secret that run needs; the CodeGraph subprocess env strips `*_API_KEY`, `GH_TOKEN`, `WHYGRAPH_GIT_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`. A `claude-cli` analyze child additionally gets `CLAUDE_CODE_OAUTH_TOKEN` (that is its one secret). Do not widen it.

CodeGraph indexing belongs to **`whygraph scan`, not the portal's Initialize step** — Initialize only bootstraps the WhyGraph DB / agent wiring / hooks / markers, and the **first scan** (run from the portal's wizard, structure only, never an LLM) builds the index. `whygraph scan` builds or refreshes the index each run — `codegraph init -i` on first run, `codegraph sync -q` thereafter — gated by `--codegraph/--no-codegraph`. CodeGraph runs from the **in-image `codegraph` binary** (no docker-in-docker, no host socket): `bootstrap.py` (`services/codegraph/`) prefers the local binary and only falls back to `docker run` on native (`uv`/`pipx`) hosts without it. There is a **single image** — `ghcr.io/mtrdesign/whygraph` — and that fallback runs `codegraph` inside it (`docker run … whygraph codegraph …`); there is no separate codegraph image.

### Auto-rescan git hooks

The portal installs them at Initialize (`hooks.py`, a top-level module beside `agents.py` / `assets.py` - there is **no** `hooks` CLI command and no `whygraph init`). Four hooks - `post-commit` / `post-merge` / `post-rewrite` / `post-checkout` - keep the DBs current as the developer works. Each execs a shared helper kept **in the git dir, not the work tree** - `$(git rev-parse --git-common-dir)/whygraph/whygraph-scan`, resolved by the dispatcher at run time so linked worktrees share it - because `.whygraph/` is gitignored and git silently overwrites an ignored file when a checkout/merge brings in a tracked one at that path, so a work-tree helper could be replaced by a hostile upstream commit and run by `post-merge`. `sync_hooks` writes it there (rename-over, never through a symlink) and removes the old `.whygraph/hooks/whygraph-scan` of earlier builds. The helper **never scans locally**: it reads `slug` and `port` from `.whygraph/portal.env` - **parsed with `sed` and validated, never sourced**, and ignored if git tracks it - and POSTs `{"trigger":"hook"}` to `http://127.0.0.1:<port>/api/projects/<slug>/scans` with `curl` (`-m 2 --noproxy '*'`, detached so commits return instantly). There is **no lock**: coalescing is the portal runner's job (one pending run per project, union of flags), so rapid commits neither stack nor drop the latest `HEAD`. When the portal is down, `curl` is missing, or `portal.env` is missing / tracked / invalid, the helper appends one line to `.whygraph/logs/hooks.log` and exits 0 (it never writes `hooks.log` or `scan.pending` through a symlink, and ignores a symlinked `.whygraph` / `portal.env`) - and the portal's **catch-up** picks the commits up: on start and every 15 minutes it queues a `hook` scan for each local project whose HEAD moved past `last_scanned_head`. The scan a hook triggers is `whygraph scan --skip-analyze --no-remote` semantics (git history + `codegraph sync` only - fast, offline, no token; LLM descriptions stay on lazy backfill or **Describe now**). Installs are **sentinel-guarded** (`# >>> whygraph managed >>>`) and append to a foreign hook rather than clobber it. The dispatcher forwards `"$@"` because `post-checkout` is the only hook git invokes with arguments; the helper's arg gate skips a file checkout and a same-commit `git switch -c`. `db/engine.py` sets `PRAGMA busy_timeout` so a background scan and a read don't collide.

`[scan].hooks` is the only switch - a bool *or* a list of hook names (four checkboxes in the portal; GitHub clones get none) - and **the portal is the reconciler**: `sync_hooks()` iterates all of `HOOK_NAMES` every time (Initialize, a `[scan].hooks` change, project removal), installing what is listed and stripping the managed block from what is not, so shrinking the list removes the dropped hooks. It is one function rather than an install/uninstall pair precisely so the removal half cannot be forgotten. It is best-effort: an unwritable hooks dir or an unknown hook name reports a `hooks_error` and the Initialize still completes.

### Branch membership

`on_default_branch` is **computed, not assumed**. `Repository.default_branch_refs` resolves the default branch (`origin/HEAD` → `<remote>/main` → `<remote>/master`, overridable via `[scan].default_branch`) and unions it with the same-named *local* branch, so unpushed commits on local `main` still count. `GitCrawler` flags new rows against that SHA set and records `first_seen_ref` (a branch name, or `refs/pull/<N>/head` for a `PROriginEnricher` recovery; `NULL` means it was on the default branch) — and a **reconcile pass** recomputes the flag for existing rows on every scan, so the DB self-heals as branches merge or get rewritten. Two guards make a mass-demotion impossible: an unresolvable default branch and a shallow clone both skip the pass entirely. Rows are never deleted — an unreachable commit is still evidence. `first_seen_ref` has exactly one consumer beyond debugging: the rename-alias walks in `mcp/path_history.py` / `mcp/evidence.py` scope to *default branch **or** current branch*, which keeps an in-flight rename visible without letting an abandoned branch pollute path history forever.

Deferred (net-new, not built yet): a project registry for cross-repo orchestration, a persistent/server mode, and per-branch CodeGraph/WhyGraph databases.

## Conventions

- **Don't add new top-level dirs** without updating `[tool.hatch.build.targets.wheel].packages` in `pyproject.toml` (currently `["src/whygraph"]`).
- **Tests live in `tests/`** (configured via `[tool.pytest.ini_options].testpaths`). `test_smoke.py` asserts the package imports and the MCP server is named `"whygraph"` — preserve both invariants when restructuring.
- **Companion repo:** CodeGraph upstream is `colbymchenry/codegraph`. WhyGraph reads its SQLite output and joins by `node_id`. Schema reference: tables `nodes`, `edges`, `files`, `nodes_fts`, `unresolved_refs`.
- **Docstrings.** All public modules, classes, and functions in `src/whygraph/` use [NumPy-style docstrings](https://numpydoc.readthedocs.io/en/latest/format.html) — sections `Parameters`, `Returns`, `Raises`, `Attributes`, `Notes`, `Examples` as applicable. Private helpers (`_foo`) get a one-line summary unless behavior is non-obvious. This overrides the global "no multi-line docstrings" default for this project. Do **not** retrofit docstrings as drive-by changes on unrelated PRs — that's a focused, standalone change.
- **Intra-package imports use the relative form.** Inside `src/whygraph/`, when a module imports from another module in the **same package**, use the relative path (`from .commit import Commit`), not the absolute (`from whygraph.services.git.commit import Commit`). Cross-package imports inside `src/whygraph/` (e.g. a `services/git/` module importing from `whygraph.core`) stay absolute. Tests and console-script entry points always use absolute imports. Don't retrofit existing absolute intra-package imports as drive-by changes — that's a focused standalone PR.

## Working principles

### 1. Think before coding

Surface assumptions before writing code. If a request has multiple plausible interpretations, name them and ask — don't pick silently.

- "Add caching for rationale cards" — in-memory per-process? On-disk under `~/.cache/whygraph`? Keyed by `node_id` or by `qualified_name + file_path`? The cache key is settled (content-addressable, so cards survive a backend swap), but TTL, location, and invalidation are open. Ask before implementing.
- "Make graph queries faster" — lower latency on a single `get_callers`, higher throughput across many calls, or perceived speed via streaming partial results? Each implies a different change.

### 2. Simplicity first

Solve today's problem with the smallest thing that works. Add abstraction when a second concrete case forces it, not in anticipation.

- For a one-off SQLite read, a function in `sqlite_codegraph_backend.py` is enough. Don't introduce a `QueryBuilder` class until a second backend actually needs to share query logic.
- The `GraphBackend` protocol is the *exception that proves the rule*: it's introduced up-front because three concrete backends are already named (`SqliteCodegraphBackend`, `JsonGraphifyBackend`, `MCPBackend`). Without that, a single backend wouldn't justify a protocol.

### 3. Surgical changes

When fixing a bug or adding a feature, change only the lines that the task requires. Don't reformat, retype, or rename code you happen to be reading.

- Fixing a crash in `get_callers` doesn't license rewriting the surrounding query, adding type hints to neighbours, or "while I'm here" docstring passes.
- Match the existing style — quote choice, import grouping, error-handling shape — even if it's not your preference. Style drift in a fix PR makes the diff impossible to review.

### 4. Goal-driven execution

Define a verifiable success criterion before changing code. Prefer small, independently-verifiable steps over a single large change.

- "Wire up `whygraph_rationale_brief`" → step 1: register the tool with a stub return and confirm it appears in the MCP Inspector's tool list (`make inspect SLUG=<slug>` against `make dev-local`); step 2: thread a `GraphBackend` lookup through it with a fixture; step 3: add real rationale assembly. Each step has its own test.
- For bug fixes, write the failing test first. If you can't reproduce the bug in a test, you don't yet understand it.

### Anti-patterns at a glance

| Principle              | Anti-pattern                                                  | Fix                                                       |
| ---------------------- | ------------------------------------------------------------- | --------------------------------------------------------- |
| Think before coding    | Silently picks one interpretation and ships it                | List the interpretations, ask which one                   |
| Simplicity first       | Protocol + factory + config dataclass for one concrete case   | One function/class until a second case appears            |
| Surgical changes       | Reformats quotes / adds type hints alongside a one-line fix   | Touch only the lines the task requires                    |
| Goal-driven execution  | "I'll review and improve the module"                          | "Failing test for X → make it pass → no regressions"      |

### Key insight

Premature complexity isn't obviously wrong — it usually follows recognisable patterns and "best practices". The problem is timing: complexity added before it's needed costs comprehension, review, test surface, and bug count, and is usually wrong about what was actually needed once a second case arrives. Solve today's problem simply; refactor when a real second case forces the abstraction.
