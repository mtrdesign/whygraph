# WhyGraph 2.0.0

!!! note "Unreleased draft"
    2.0.0 is not released yet. This page describes the changes on their way and may move until the
    release is tagged.

2.0.0 turns WhyGraph from a per-repository command line tool into a local **portal**: one server that
holds all your projects, runs their scans, and serves an MCP endpoint per project. Your history carries
over, but how you start WhyGraph, where keys live, and how agents connect all change. Read the breaking
changes before you upgrade.

The same release adds an opt-in **production mode** for running the portal for a team, and **connected
portals** that let a developer's local portal answer for a project hosted on a production one.

## Breaking changes

- **`whygraph init`, `whygraph serve`, `whygraph analyze` and `whygraph-mcp` are removed.** Add a
  repository from the portal's Projects page instead of running `init`; the portal is the web panel that
  `serve` used to start; per-commit descriptions come from `scan` and from **Describe now**. `init`,
  `serve` and `whygraph-mcp` remain only as stubs that print a pointer to the portal and exit with status
  `2`. `analyze` is gone entirely.
- **Agent configs are now HTTP.** Every agent (Claude Code, Cursor, VS Code / Copilot, Codex) connects
  to `http://localhost:<port>/mcp/<slug>` instead of launching a stdio server. To migrate, re-add each
  repository in the portal: it offers to migrate or remove each old `whygraph` entry per agent file.
- **The installer replaces the `whygraph-mcp` shim with a stub** that prints the removal message, so a
  stale 1.x agent config that still runs `whygraph-mcp` fails with an explanation rather than a bare
  "not found".
- **`whygraph scan` refuses in portal-managed repositories.** Scan from the portal. Headless `scan` still
  works in a repository the portal does not manage (CI, a plain checkout), and in one you have removed
  from the portal.
- **Git hooks require the running portal.** Hooks no longer run a local scan; they ask the portal to
  scan. Commits made while the portal was down are caught up the next time it starts. The hook helper now
  lives inside the git directory at `.git/whygraph/whygraph-scan` (not in `.whygraph/hooks/`), and is never written through a symlink.
- **API keys and GitHub tokens in your shell env no longer reach WhyGraph.** The portal container is
  started with none of your environment, so exporting `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` or `GH_TOKEN`
  has no effect on it or on the scans it runs. Enter them in the portal's **Settings**. Keys and tokens
  already written in a repository's `whygraph.toml` are moved into the portal's encrypted store when the
  file is imported. Headless `whygraph scan` outside the portal still reads the standard variables.
- **The `claude-cli` provider is removed.** It ran the Claude Code CLI on your Claude subscription.
  Anthropic's terms do not allow third-party tools to collect or store Claude subscription credentials,
  or to route requests through Free, Pro or Max plan credentials (see
  [Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance)), so
  WhyGraph no longer offers it, and the image no longer ships the Claude Code CLI. Use the `anthropic`
  provider with an API key instead, or another provider such as `openrouter`. A leftover `claude-cli`
  setting (an `[llm.claude_cli]` table, a `"claude-cli/..."` model, a task's `provider = "claude-cli"`)
  is ignored with a warning and the task falls back to the default provider; importing a
  `whygraph.toml` that has one lists it in the preview's warnings. The portal clears stored
  `claude-cli` settings and deletes any stored Claude subscription token. Claude Code as an agent that
  connects to WhyGraph's MCP endpoint is unaffected. See
  [LLM providers](../reference/llm-providers.md#claude-cli-removed).
- **Deprecated config keys.** These 1.x keys still work in 2.x, log one deprecation warning per process,
  and **stop being supported in 3.0**:

    | 1.x key | Use instead |
    |---|---|
    | `[scan].provider` | `[scan].forge` |
    | `[scan].max_workers` | `[analyze].max_workers` |
    | `[llm.<provider>].model` | `[llm].model = "<provider>/<model>"`, or a task's own `model` (`[<task>].model`) |
    | Task-level `timeout_sec` (`[analyze].timeout_sec`, `[rationale].timeout_sec`) | `[llm.<provider>].timeout_sec` |

    A 1.x file resolves to the same providers, models and timeouts it did before. See
    [Deprecated keys](../reference/configuration.md#deprecated-keys).

## Upgrade path

1. Install 2.0.0 with the [installer](../getting-started/installation.md). If you ran the old
   playground, `whygraph serve --stop` removes a leftover container that may hold port 8765.
2. Start the portal and share the folder that holds your repositories:

    ```bash
    whygraph up --add-folder ~/Work
    ```

    `whygraph up` also starts a second container, `whygraph-portal-postgres`, for the portal's own
    database, and waits for it to be ready (see [Footprint](#footprint)).

3. Add each existing repository from the Projects page, exactly like a new project. **Their data is
   reused**: `.whygraph/whygraph.db` is backed up and migrated, the `.codegraph/` index is kept, 1.x hooks
   are replaced by the portal's, and old agent entries are migrated to HTTP.
4. Enter your provider keys and GitHub token under **Settings**.

The [full upgrade guide](../portal/upgrading.md) covers custom database paths, agent approval prompts
and going back.

## What's new

- **The portal.** `whygraph up` starts one local server for every project, with setup, a Projects page,
  an add-project wizard, per-project settings and global Settings. The Explorer and Chat assistant move
  into it, one per project.
- **Usage & cost.** Every LLM call the portal makes is recorded (tokens, an estimated cost, who
  triggered it, which project and model), with a **Usage & cost** page to explore it - by project,
  model, member and machine, down to the single call, with CSV export. Owners and admins see everyone,
  members see their own **My usage**. **Monthly budgets** per organization, project and member alert at
  50, 75 and 100% and can **hard stop** LLM spend (chat, new rationale cards, full scans) while reads
  and quick scans keep working. Prices are a bundled table an organization can override; the agent
  limits gain per-member limits under the organization ceiling. See
  [Usage & cost](../portal/usage.md).
- **A database container.** The portal keeps its own data - the project list, settings, encrypted keys
  and scan history - in Postgres. `whygraph-portal-postgres` publishes no port; only the portal reaches
  it, over its private Docker network. Its files are in `postgres/` in the data directory, owned by you,
  and its password is a generated `0600` file there, never an environment value. `whygraph down` stops
  both containers, and `whygraph status` reports both (and exits non-zero unless both run). Each
  project's `.whygraph/whygraph.db` and `.codegraph/` stay SQLite, in the repository.
- **`whygraph backup`.** Dumps the portal database into `backups/` in the data directory, keeping the
  newest 10. `whygraph up` makes the same dump automatically before it recreates a running database
  container (`WHYGRAPH_SKIP_BACKUP=1` skips it). See [Backup and restore](../portal/backup.md), and
  back up `secret.key` with the dumps.
- **One portal per database.** Beside the lock on its data directory, the portal holds a lock on its
  database, so a second portal pointed at the same database starts degraded instead of running
  alongside the first. `whygraph up` waits for the database's health check before starting the portal,
  and a portal that cannot reach its database within a minute exits so Docker retries it.
  `WHYGRAPH_POSTGRES_IMAGE` overrides the pinned Postgres image for a registry mirror; see
  [Configuration](../reference/configuration.md#environment-variables).
- **Per-project HTTP MCP.** Each project gets its own endpoint at `/mcp/<slug>`; the portal writes and
  migrates the config for all four agents.
- **Config v2.** One `[llm]` table with `provider/model` names, per-task overrides, and a forge setting;
  1.x files keep working.
- **Live scans.** Scans run inside the portal with streamed progress, run history and a log tail, an
  estimate up front, and single-flight runs that merge queued triggers.
- **A design system.** The playground is rebuilt on shadcn primitives and design tokens, with a light
  and dark theme.
- **Security hardening.** Host, Origin and fetch-metadata guards on the API, credentials in an encrypted
  store with a rotatable keyring, a path check that never follows a symlink out of a project root,
  configured remotes that can never become git options, and atomic project removal.

## Production mode

A **production mode** runs the portal for more than one person. It is off unless you start the portal
with `WHYGRAPH_MODE=production`; local mode looks and behaves exactly as described above. Setup is in
[Run in production](../deploy/production.md).

- **Accounts.** A fresh production portal is claimed with a one-time bootstrap secret printed in its
  log, which creates the first instance admin. After that people sign in with GitHub (an OAuth App you
  create, two-factor authentication required); the bootstrap admin keeps an email and a password (15
  characters or more, checked against a blocklist). Sessions are kept on the server; no email is sent
  and none is stored for GitHub users.
- **Organizations on their own hosts.** Any signed-in user can create an organization, which lives on
  `<org>.<your host>` with the session cookie set on the base host. The portal checks membership on
  every request and refuses a write from one organization's page to another's host.
- **Instance admins** manage users and admins, issue one-time reset links, and can read every
  organization (read-only, and logged).
- **A deployment bundle.** `docker/production/` holds a compose file for the portal, Postgres and a
  Caddy that obtains a wildcard certificate by DNS-01.
- **Members and access.** Owners and admins invite people by GitHub username; an invitation is redeemed
  when that account signs in, and no mail is sent. Each project gives every member an effective role -
  Admin, Contributor or Viewer - from their organization role, the organization's default and
  per-person grants; a **Restricted** project is visible only to the people granted it. Only project
  admins start a scan that spends LLM tokens, and viewers spend nothing. Owners can rename the
  organization, set its default project role and transfer ownership; instance admins can disable
  accounts. See [Members](../deploy/production.md#members).
- **A security event log.** Sign-ins, membership, access and budget changes are recorded in the
  portal's database for 400 days, on an owner-only **Audit** page with CSV export. See
  [The security event log](../deploy/production.md#the-security-event-log).
- **Projects from GitHub.** Owners and admins import repositories through a GitHub App you create,
  with repository-scoped, read-only installation tokens; GitHub's push webhooks and an hourly check
  keep each server copy current, and a project that loses access stays readable. Owners can delete an
  organization, and its slug is retired. See [The GitHub App](../deploy/production.md#the-github-app).
- **New variables:** `WHYGRAPH_MODE`, `WHYGRAPH_BASE_URL`, `WHYGRAPH_TRUSTED_PROXIES`, the
  `WHYGRAPH_GITHUB_*` sign-in settings and the five `WHYGRAPH_GITHUB_APP_*` ones; see
  [Configuration](../reference/configuration.md#environment-variables). A refused production start
  exits with status `2`.

A production portal serves no `/mcp` endpoint of its own; agents reach its projects through a
developer's local portal (below). Sign-up is open to any GitHub account with two-factor
authentication and cannot be closed yet, so restrict network access to the base host.

## Connected portals

A developer can link a checkout on their machine to a project on a production portal (a
**platform**), and their agent keeps using the **local** portal's `/mcp/<slug>`. The local portal
blames the working tree itself and asks the platform about the **pushed** commits, so uncommitted and
unpushed work stays on the laptop and no shared history is stored there. See
[Projects from a platform](../portal/platform-projects.md).

- **A third project source.** In local mode, **New project** gains **From a platform**; a platform
  project is linked in one browser round trip and has no local WhyGraph database. Its scans build the
  CodeGraph index only, and its Explorer and Chat are on the platform.
- **Connection tokens.** A platform issues one token per project and person after an
  OAuth 2.0 authorization code with PKCE and an `iss` check. It is encrypted in the local portal's
  database, re-checked against the person's membership on every call, and revoked when they are
  removed, disabled or remove the link. See the [security model](../portal/security.md#connected-portals).
- **A versioned `/api/v1`** on the platform's organization hosts, accepting bearer tokens only, with
  evidence, rationale, area history, commit, pull request, issue and overview routes.
- **Connected portals lists.** Each person sees their own on the Account page, and project owners and
  admins see (and can revoke) every member's, including the machine name. See
  [Run in production](../deploy/production.md#connected-portals).
- **Agent limits.** Organization-only settings bound the model spend agents can trigger on a
  platform: `[rationale].agent_generations_per_hour` (default 120) and
  `[analyze].agent_descriptions_per_hour` (default 600) for the whole organization, and
  `[rationale].agent_generations_per_member_per_hour` (30) and
  `[analyze].agent_descriptions_per_member_per_hour` (150) for each member. See
  [Configuration](../reference/configuration.md#agent-limits-organization-only).
- **New MCP fields.** A linked project's results carry a `platform` block, and commits the platform
  cannot supply carry a `push_status`. See the [MCP reference](../reference/mcp.md#linked-projects).
- **Your machine's name.** `whygraph up` starts the portal container with your host's short name, which
  the connect page offers as the name of the connection. A changed name recreates the container, like
  a changed port or folder.

## Footprint

The database container uses about **30 MiB of RAM** when idle, and the first `whygraph up` pulls the
`postgres` image from Docker Hub once. On a network that blocks Docker Hub, point
`WHYGRAPH_POSTGRES_IMAGE` at a mirror of the same image.

## For developers

- `uv run pytest` needs Docker (it starts a throwaway Postgres) or `WHYGRAPH_TEST_DATABASE_URL`.
- `make dev-local` runs against `make dev-db`, a dev Postgres on `127.0.0.1:55432`, and its Vite
  server is on `:5174` so it can run beside `make dev-production`.

See [Developing WhyGraph](../guide/developing.md#the-portal-database-in-development) and
[Linking the two dev portals](../guide/developing.md#linking-the-two-dev-portals).
