# WhyGraph 2.9.0

Plans your team commits are now shared on the platform. The scan indexes the Markdown plans under
`[plans].dir` (default `docs/plans`), links each one to the code it built, and agents get short
pointers to them as intent, ranked below commits and PRs. `/whygraph-implement` publishes its plan
after a passing run, and each project gets a read-only Plans page.

!!! note "Upgrading and rolling back"
    From 2.8.0, run `whygraph update` (locally) or move the production image tag to `2.9.0`, then
    **Settings > Update agent files** in each project to get the publish step and the new
    `portal.env` line. Each project's database gets two new tables on first use. A linked portal
    works with an older platform (it reports plans as `unsupported`), but plans reach a linked
    checkout only when its platform runs 2.9.0. To go back, see
    [Rolling back after this release](#rolling-back).

## What's new

- **Shared plans.** A plan your team commits is now part of what WhyGraph knows. The scan has a new
  **Plans** phase that indexes the Markdown files under `[plans].dir` (default `docs/plans`) from
  `HEAD`'s git objects, with no model call, and links each plan to code through `WhyGraph-Plan:` lines
  in commit messages and PR descriptions and through the paths the plan names. A plan's status
  (`shipped`, `in_flight` or `not_implemented`) is derived from those links, and a commit or PR that
  only adds the plan file does not count. Indexing is on by default; set `[plans].dir` to `""` under
  **Settings > Plans** to turn it off. See [Sharing plans with your team](../guide/planning.md#sharing-plans).
- **Publish a plan.** A passing `/whygraph-implement` run copies its plan into the plans folder on its
  own and prints the `git add` line (opt out with `--no-publish`). `/whygraph-plan --publish <stem>
  [--force]` does it on demand. A re-publish replaces WhyGraph's own earlier copy but never one you
  edited by hand unless you pass `--force`. The implementor now writes `WhyGraph-Plan: <stem>` on the
  commits it makes. Nothing is committed for you: commit the published plan with your change.
- **Plans for agents, as intent.** `whygraph_rationale_brief` and `whygraph_area_history` may carry a
  short `plans` list of pointers, and two new resources, `whygraph://plan/{stem}` (a decision digest
  and contents) and `whygraph://plan/{stem}/section/{n}` (one section of at most 8,000 characters),
  are the only way plan text reaches an agent. Beside a rationale card only plans whose commits or
  PRs touched the symbol's own lines, or a shipped plan that declares a change to it, appear (at most
  three), and a plan never enters the card itself. `whygraph_evidence_for` carries none. See
  [the MCP reference](../reference/mcp.md#plans).
- **A Plans page.** A read-only page per project lists the committed plans with status tabs and search
  and opens a plan with its commits, PRs and paths. The Explorer's Rationale tab links the plans
  behind a symbol, and **Settings > Plans** turns indexing off or changes the folder.
- **Linked checkouts.** A linked portal asks its platform for the plans of the history and cards it
  already requested, sending nothing new, and reads plan digests and sections through it.
- **`plans_dir` in `portal.env`.** The untracked `.whygraph/portal.env` gains a third line so every
  editor, VS Code included, publishes into the right folder.

## Rolling back { #rolling-back }

This release adds two tables to each project's WhyGraph database (the portal's own database is
unchanged). An older image cannot open an upgraded project database: to go back, restore each
project's `backups/whygraph-e9b3d6a1c5f8.db`, which the portal writes beside its `whygraph.db` before
upgrading it, then re-run the installer from the `v2.8.0` tag and `whygraph up` (`whygraph update`
refuses a downgrade). Published plan files in your repositories stay where they are.

## For developers

- **Project database migration** `b6f2a9c4d815`: the `plan` table (one row per indexed plan: path,
  blob, digest, outline, why index, redacted body up to 512 KiB) and `plan_link` (commit, PR and path
  links). Neither is part of a project transfer; both are rebuilt by the next scan.
- **Three `/api/v1` routes**: `POST /api/v1/projects/{slug}/plans/for`, `GET .../plans/{stem}` and
  `GET .../plans/{stem}/sections/{n}`, behind the new `plans` capability at `/meta`. `API_VERSION` is
  unchanged (2), and the project status block gains `plans_dir`.
- **`plan-tool.sh`** gains `publish` and `plans-dir` in all four agent trees.
